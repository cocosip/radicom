### Behaviour / API changes introduced by the fixes

- New `anonymizer::AnonOptions` (bitmask) and `Anonymizer::with_profile(profile, impl Into<AnonOptions>)`;
  a single `AnonOption` now implies `BasicProfile | it`, so existing single-option calls keep working and
  are safe. Import `AnonOption`/`AnonOptions` from `radicom::anonymizer`.
- `model::element::FromLeBytes::from_le_widened` gained a `sign: bool` parameter (a low-level public
  trait; called by the crate's typed accessors) so unsigned VRs zero-extend.
- `CFindResponse` gained `affected_sop_class_uid`; its wire command set now carries `(0000,0002)` and no
  longer carries `(0000,1020..1023)`. The one golden `tests-data/goldens/cmd_cfind_pending_rsp.hex` was
  regenerated for this intentional wire change.
- Saving a file now re-derives `MediaStorageSOPInstanceUID (0002,0003)` from the dataset's
  `SOPInstanceUID (0008,0018)`; a previously stale value is corrected on save.
- Private sequences are written with undefined length under Implicit VR (defined length stays for
  Explicit VR), so they round-trip without a private dictionary on the read side.
- `PixelData::high_bit()` derives `BitsStored-1` when `(0028,0102)` is absent.
- Print Min/Max Density now uses the same optical-density convention as `PrintDensity::background`
  (default window `0..200` hundredths = identity).
- `Uid::storage_category` compares the standard root on a component boundary.
- `ValidationScopeGuard` is now per-thread; it no longer silences validation on other threads.

### Deliberately retained limits (not defects)

- The read-side 256 KiB PDU cap is kept for A-ASSOCIATE too: PS3.8's Max-PDU-Length formally governs
  only P-DATA-TF, but raising the cap only enlarges a read-side allocation surface and real associations
  are tiny. Documented deviation.
- Biplane XA/XRF (`1.2.840.10008.5.1.4.1.1.12.3`) is not added to the modality-LUT skip list because it
  has no generated UID constant and the CI UID guard forbids a raw literal; add it via the dictionary
  generator, then extend `is_xa_xrf`.
- An external private SQ written with a *defined* length under Implicit VR still needs a private
  dictionary to recover its structure (bytes are preserved).
- CP-246 `explicit_vr=false` is applied to the Big-Endian UN-undefined-SQ case only; applying it to
  Little Endian would violate the project's existing `t3_un_undefined_length_parsed_as_sq` behaviour and
  real LE files that encode UN-SQ content explicitly. The large-length misparse that motivated IO-04 is
  covered by a BE regression test.

## P0 / P1 — confirmed and independently re-verified

### FJ-01 (P0) — Anonymizer options drop the entire Basic Profile → PHI leak

- **Location:** `crates/radicom/src/anonymizer/mod.rs:36-43,130`; `anonymizer/profile.rs:369-391`.
- **What happens:** `AnonOption` is a single exclusive enum; `action_for_tag` reads exactly one
  column of the 11-column PS3.15 table. In `ps3.15.csv` the Basic-Profile actions live only in
  column 0 (`0010,0010;Z;;;;;;;;;;`); columns 1-10 contain a cell only for the attributes that
  option changes. Therefore `Anonymizer::with_profile(SecurityProfile::basic(), AnonOption::RetainUids)`
  returns `None` for PatientName/PatientID/etc., which are left in place.
- **Why it is wrong:** fo-dicom's `SecurityProfileOptions` is a `[Flags]` enum; `LoadProfile`
  iterates every *enabled* column and lets a non-empty cell override the Basic action. The
  intended call is `BasicProfile | RetainUids`, which still blanks PatientName. The Rust API
  cannot express the combination, and the natural call is silently unsafe.
- **Evidence:** verified against
  [fo-dicom `DicomAnonymizer.cs`](https://raw.githubusercontent.com/fo-dicom/fo-dicom/d3e6b48426866fa7bf5a52414acca4898f73b6da/FO-DICOM.Core/DicomAnonymizer.cs)
  (`LoadProfile` loops `for i … if ((options & flag) == flag) { var action = parts[i+1] … if (action != empty) profile[tag] = … }`).
- **Fix:** model the selection as a flag set (`bitflags`, or `&[AnonOption]`) and resolve, per tag,
  the Basic column first then each enabled option's non-empty cell (fo-dicom order). At minimum,
  make non-Basic options imply `BasicProfile` and add a regression test asserting PatientName is
  blanked under every option.

### IO-01 (P1) — `TransformRule::CopyValue` silently empties string values

- **Location:** `crates/radicom/src/rules/transform.rs:94-104` (with `io/writer.rs:159-168,464-483`,
  `model/element.rs:136-138`).
- **What happens:** `CopyValue` builds the destination with `DicomElement::new_bytes(dst, vr, e.encoded())`.
  For a string VR that stores the value as `Bytes`; `DicomWriter::encode_value` then encodes string
  VRs from `string_value()`, which is `""` for `Bytes`, so the copied element is written with
  length 0.
- **Why it is wrong:** the value is silently lost on save while in-memory reads appear correct.
- **Evidence (code):** `encode_value` returns `Some(Vec::new())` for a byte-backed string element;
  `write_item` takes the `Some(value)` branch and writes an empty leaf. The existing `copy_value`
  test only checks the in-memory dataset.
- **Fix:** preserve the value representation, e.g. retag the source item
  `DicomItem::Element(e.clone().with_tag(dst.clone()))` (`with_tag` is already `pub(crate)`), or
  build a `Str` element for string VRs and pass the buffer through for binary VRs. Add a
  write→reparse round-trip test.

### PR-01 (P1) — `PixelData::high_bit()` defaults to 0, corrupting frames that omit HighBit

- **Location:** `crates/radicom/src/pixel/mod.rs:127-129`; consumers `render/mod.rs:713,1235,1777,1823,1897`,
  `render/reconstruction.rs:388`.
- **What happens:** when `(0028,0102)` High Bit is absent, `high_bit()` returns 0. Every render/MPR
  path builds `BitDepth::new(..., high_bit=0, ...)`; `BitDepth::normalize` then masks to
  `(1 << 1) - 1` and shifts, so an 8-bit frame becomes 0/128 per pixel and a 16-bit frame 0/32768.
- **Why it is wrong:** High Bit is Type 1 and equals `BitsStored-1`; fo-dicom's
  `BitDepth.FromDataset` derives it from `BitsStored`/signedness and never consults the tag.
  `pixel/overlay.rs` already derives the correct default, so this is confined to render/MPR.
- **Scope caveat:** only triggers when the mandatory tag is absent (non-conformant/legacy input).
  Confirm against the corpus before deciding P1 vs P2.
- **Fix:** `self.dataset.get_or(HIGH_BIT, self.bits_stored().saturating_sub(1))`, or derive from
  `BitsStored`; keep the explicit tag when present.

### NW-01 (P1) — C-FIND-RSP omits the mandatory Affected SOP Class UID (0000,0002)

- **Location:** `crates/radicom-network/src/cfind.rs:292-306` (and `CFindResponse` struct). Every
  C-FIND response a radicom SCP emits is built here.
- **What happens:** `CFindResponse::to_command` never sets `affected_sop_class_uid`, so the command
  set omits `(0000,0002)`.
- **Why it is wrong:** PS3.7 Table 9.3-4 lists Affected SOP Class UID as a required field of
  C-FIND-RSP (verified against the current standard text:
  <https://dicom.nema.org/medical/dicom/current/output/chtml/part07/sect_9.3.2.2.html>). C-MOVE-RSP,
  C-GET-RSP and C-STORE-RSP in this crate all set it; C-FIND is the lone exception. fo-dicom's
  `DicomCFindResponse` carries the SOP Class UID from the request. radicom↔radicom self-interop
  hides it because `from_command` ignores the field.
- **Fix:** add `affected_sop_class_uid: String` to `CFindResponse`, populate it in
  `pending/success/failure/from_command`, and set it in `to_command`; assert presence in a test.

## Cross-cutting observations

1. **Prior "no blocking finding" was not supported.** The earlier repair round concluded no
   blocking finding remained; this pass found a PHI leak and three P1s, several of which were exactly
   the kind of thing its "checked and clean" lists asserted. Treat earlier review snapshots as
   historical, not as a current guarantee.
2. **Tests mask defects.** Several bugs survive because a test asserts the buggy value: CM-01
   (accepts `Us`), FJ-02 (only midpoint), NW-01 (self-interop ignores the field), NW-03 (never
   checks `(0000,0800)`), IO-01 (in-memory only). Regression tests should pin the *output bytes* or
   the *external contract*, not the in-memory view.
3. **Recurring root causes** are few: (a) type/VR information is thrown away at a boundary
   (CM-01/02/08, IO-01, FJ-03/04); (b) one option/priority is hard-selected instead of composed
   (FJ-01, PR-10, CM-04); (c) peer- or config-supplied sizes are trusted (NW-04, IO-05, PR-08).

## Recommended remediation order

1. **FJ-01** (PHI leak) — API change; decide flags vs. documented Basic implication, add tests.
2. **IO-01, PR-01, NW-01** — small local fixes plus byte/contract regression tests.
3. **NW-03, NW-04** — one-line dataset-type fix and a max-PDU clamp (cheap DoS hardening).
4. **FJ-02, FJ-03, IO-02, PR-03** — output-correctness fixes with white/black and round-trip tests.
5. **CM-01/02/03 and the P3s** — batch by module; add the missing edge-case tests.
